# floats

[![CI](https://github.com/go-simd/floats/actions/workflows/ci.yml/badge.svg)](https://github.com/go-simd/floats/actions/workflows/ci.yml)
![coverage](https://img.shields.io/badge/coverage-100%25-brightgreen)
[![Go Reference](https://pkg.go.dev/badge/github.com/go-simd/floats.svg)](https://pkg.go.dev/github.com/go-simd/floats)

SIMD-accelerated reductions over `[]float32` and `[]float64` — the dot product,
sum, min, max, Euclidean (L2) distance and cosine similarity that sit at the
heart of **vector search, embeddings and numerics**, plus the float64
`Axpy`/`Xpby`/`AxpyDot`/`Scale` updates behind iterative solvers and the
`Mul`/`Axpby3`/`Clamp`/`MaxAbs` kernels of splitting QP solvers, and the
NumPy-exact `SumPairwise` and unfused `AxpyNoFMA`/`AxpyDiffNoFMA`/… kernels
(bit-identical to `np.sum` and to `a + F*(b - c)`). Pure Go: `CGO_ENABLED=0`,
stable Go, no `GOEXPERIMENT`. The hot reduction loops are real FMA SIMD on **all
six 64-bit Go targets**, assembly generated by
[go-asmgen](https://github.com/go-asmgen/asmgen) — on a plain `go build`.

```go
import "github.com/go-simd/floats"

sim := floats.CosineSimilarity(query, doc)        // []float64 relevance score
d   := floats.Float32Distance(embA, embB)         // []float32 L2 distance
dp  := floats.Dot(a, b)                            // a·b
```

## API

For `[]float64` (top-level) and `[]float32` (the `Float32*` functions):

| float64 | float32 | meaning |
|---|---|---|
| `Dot(a, b)`              | `Float32Dot(a, b)`              | a·b = Σ aᵢbᵢ |
| `Sum(a)`                 | `Float32Sum(a)`                 | Σ aᵢ |
| `Min(a)` / `Max(a)`      | `Float32Min(a)` / `Float32Max(a)` | min / max element (NaN-propagating; `-0 < +0` as NumPy: max of a mix with a `+0` is `+0`, min of a mix with a `-0` is `-0`) |
| `Distance(a, b)`         | `Float32Distance(a, b)`         | ‖a−b‖₂ = √Σ(aᵢ−bᵢ)² |
| `CosineSimilarity(a, b)` | `Float32CosineSimilarity(a, b)` | a·b / (‖a‖₂‖b‖₂) |

`Dot`, `Distance` and `CosineSimilarity` require `len(a) == len(b)` and panic
otherwise; `Min`/`Max` panic on an empty slice; `Sum` of an empty slice is 0.
The float32 dot/sum/squared-difference are accumulated in float32; cosine and
distance take the final square root in float64 for accuracy.

### Elementwise updates (BLAS level 1, float64)

The in-place updates that iterative solvers (CG, GMRES), Householder QR and LU
elimination spend their time in:

| function | computes |
|---|---|
| `Axpy(alpha, x, y)`       | `y[i] = math.FMA(alpha, x[i], y[i])` (y += αx) |
| `Xpby(x, beta, y)`        | `y[i] = math.FMA(beta, y[i], x[i])` (y = x + βy) |
| `AxpyDot(alpha, x, y, w)` | Axpy, then returns Σ `y[i]*w[i]` over the updated y, in one pass |
| `Scale(alpha, x)`         | `x[i] *= alpha` |

```go
// one conjugate-gradient step
floats.Axpy(alpha, p, x)              // x += αp
rr := floats.AxpyDot(-alpha, ap, r, r) // r -= αAp, rr = r·r
floats.Xpby(r, rr/rrOld, p)            // p = r + βp
```

They operate on the first `len(x)` elements and panic if `y` (or `w`) is
shorter. `y` may be the same slice as `x` or `w`; partially overlapping slices
are not supported.

**Bit-identical on every architecture.** Each updated element is rounded once,
exactly as `math.FMA` rounds it: `VFMADD` on amd64 (AVX2+FMA), `VFMLA`/`FMADDD`
on arm64, the `math.FMA` loop everywhere else (one hardware FMA instruction on
ppc64le, s390x, riscv64 and loong64). The updated slice never depends on the
architecture or the CPU features detected at run time (NaN payloads aside).
This is *not* the unfused `y[i] + alpha*x[i]` that amd64 Go code computes, so
replacing such a loop can change the last bit; the fused result is the more
accurate one. `AxpyDot`'s returned sum is a reduction and follows the
lane-order rules of [Floating-point determinism](#floating-point-determinism).

| arch | elementwise kernel |
|---|---|
| amd64 | AVX2+FMA, ×4 unrolled (16 elements/iteration), gated on `HasAVX2 && HasFMA` |
| arm64 | NEON, ×4 unrolled (8 elements/iteration, four-register `VLD1`/`VST1`) |
| ppc64le, s390x, riscv64, loong64 | portable `math.FMA` loop: no kernel until one is measured on the real silicon, as for the reductions |

### Gather kernels (index list, float64)

The free-set operations of bound-constrained solvers (L-BFGS-B subspace
minimisation, active-set QP): vectors read through a list of active indices.

| function | computes |
|---|---|
| `DotIdx(a, b, idx)`          | Σₖ `a[idx[k]]*b[idx[k]]` |
| `DotGather(a, idx, d)`       | Σₖ `a[idx[k]]*d[k]` (`d` contiguous, `a` gathered) |
| `AxpyGather(alpha, a, idx, d)` | `d[k] = math.FMA(alpha, a[idx[k]], d[k])` for every k |

They are portable Go (no assembly yet; a SIMD gather can replace them behind
the same signatures). They panic if an index is out of range or
`len(d) < len(idx)`. Repeated and unordered indices are allowed.

**Accuracy contract.** The two sums use four FMA accumulators over
lane-blocked groups of four indices (`k mod 4`), combined as
`(s0+s1)+(s2+s3)`: they are **not** summed left to right, so the last bit
differs from the obvious loop. The stated bound, asserted against a 300-bit
`math/big` oracle, is |result − exact| ≤ n·ε·Σₖ|aᵢbᵢ| with ε = 2⁻⁵² (plus an
absolute 2⁻¹⁰⁷⁴ term per element when products underflow to subnormals).
`AxpyGather` rounds each element once and is bit-identical everywhere.

### Products, combinations, clamping, infinity norm (float64)

The vector kernels of splitting solvers (ADMM / OSQP-style quadratic
programming): the product with a diagonal, the three-term update, the projection
onto a box and the ∞-norm of a residual.

| function | computes |
|---|---|
| `Mul(dst, a, b)`                              | `dst[i] = a[i]*b[i]` |
| `Axpby3(dst, alpha, a, beta, b, gamma, c)`    | `dst[i] = math.FMA(gamma, c[i], math.FMA(beta, b[i], alpha*a[i]))` (αa + βb + γc, fused) |
| `Clamp(dst, v, lo, hi)`                       | `dst[i] = min(max(v[i], lo[i]), hi[i])`, with the exact NaN and signed-zero rules below |
| `MaxAbs(v)`                                   | the largest `abs(v[i])` (the ∞-norm); 0 for an empty slice |

```go
// one ADMM-style step: z = Π_[l,u](α·Ax + (1−α)·z_prev + y/ρ)
floats.Axpby3(t, alpha, ax, 1-alpha, zPrev, 1, yOverRho)
floats.Clamp(z, t, l, u)
rNorm := floats.MaxAbs(r)
```

Like the updates above they work on the first `len(a)` (`len(v)`) elements,
panic if another slice is shorter, and allow `dst` to be the same slice as an
input. All four are **bit-identical on every architecture**: `Mul` is one IEEE
multiply per element; `Axpby3` **is fused** — two `math.FMA` steps after the
rounded product `alpha*a[i]`, so it differs from the unfused
`alpha*a[i] + beta*b[i] + gamma*c[i]` by at most a few ULP of `Σ|terms|` (the
tests check that tolerance and also that the fused form is what runs); `Clamp`
and `MaxAbs` round nothing.

`Clamp` is `r := v[i]; if lo[i] > r { r = lo[i] }; if hi[i] < r { r = hi[i] }`:
a NaN `v[i]` comes out unchanged (same bits, either sign); a NaN bound is ignored
(that side is unbounded); `lo[i] > hi[i]` gives `hi[i]`; signed zeros compare
equal, so the result is `v[i]` unless a strict bound replaces it. `MaxAbs`
returns `math.NaN()` if any element is NaN (either sign, quiet or signaling) and
`+Inf` if there is an infinity and no NaN; an all-zero slice gives `+0`.

| arch | kernels |
|---|---|
| amd64 | AVX2+FMA, ×4 unrolled (`VMULPD`, `VFMADD231PD`, `VMAXPD`/`VMINPD` with the operand order that gives the strict compare, `VANDPD` + `VMAXPD` + an unordered-compare NaN mask), same `HasAVX2 && HasFMA` gate |
| arm64 | NEON, ×4 unrolled (`VFMUL`, `VFMLA`, `VFCMGT` + `VBIT` — not `FMAX`/`FMIN`, which treat NaN bounds and signed zeros differently —, `VFABS` + `VFMAX`) |
| ppc64le, s390x, riscv64, loong64 | the portable loops, as for the updates above (`Mul` has a kernel there, see below) |

### `OverlapWindow`, `Float32OverlapWindow`: windowed overlap-add of lapped transforms

| function | computes (n = len(a), j = n-1-i) |
|---|---|
| `OverlapWindow(dst, a, b, win)` / `Float32OverlapWindow(...)` | `dst[i] = a[i]*win[2n-1-i] - b[j]*win[i]`, `dst[2n-1-i] = a[i]*win[i] + b[j]*win[2n-1-i]` for `i < n` |

The inner loop of the synthesis of every MDCT codec (AAC, Vorbis, Opus CELT, AC-3,
MP3): the second half of the previous block and the first half of this one are
combined under a window, so that the time-domain aliasing cancels. `b`, `win` and
`dst` are read and written from both ends, which the auto-vectoriser cannot do; the
kernels reverse a register instead. The contract is a bound, not bit identity: each
output is within 2 units of the last place of its two products' magnitudes of the
exact value (`TestOverlapWindowBound` against a 200-bit computation, float32 and
float64, every size from 1 to 1024). arm64 NEON (`VREV64`+`VEXT`, `VFMUL`,
`VFMLS`/`VFMLA`; 4 float32 or 2 float64 lanes) and amd64 AVX2+FMA (`VPERMILPS` +
`VPERM2F128` or `VPERMPD`, `VFNMADD231`/`VFMADD231`; 8 or 4 lanes), generated by
go-asmgen (`overlap_*_gen.go`); the portable loop elsewhere and on an amd64 CPU
without AVX2+FMA. On an Apple M4 Max, 1024 steps: float32 764 to 212 ns (3.6x),
float64 789 to 377 ns (2.1x) against the portable loop. Wanted by go-avkit/decode
(AAC) and go-fft's TDAC helper.

### `CMulGather`, `CMulScatter`: the twiddle passes of the DCT-IV and the MDCT

| function | computes (n = len(tw), a complex number is two consecutive float64) |
|---|---|
| `CMulGather(dst, x, tw)` | for `m < n/2`: `dst[2m] = x[2m]*tw[2m] - x[n-1-2m]*tw[2m+1]`, `dst[2m+1] = x[2m]*tw[2m+1] + x[n-1-2m]*tw[2m]` |
| `CMulScatter(dst, c, tw, f)` | `z = tw[m]*c[m]` (complex), `dst[2m] = f*Re z`, `dst[n-1-2m] = -f*Im z` |
| `CMulGatherFrom32(dst, x, tw)` | `CMulGather` with `x` float32, widened in the kernel |
| `CMulScatterTo32(dst, c, tw, f)` | `CMulScatter` with `dst` float32, each output rounded once |

A DCT-IV of even length is an n/2-point complex FFT between two passes over the
data: the real input is read as complex pairs of its even samples and its odd
samples from the end, multiplied by a table; the FFT's output is multiplied by a
table and written back, real parts to the even positions and negated imaginary
parts to the odd ones from the end. Those passes are more than half of a small
DCT-IV or MDCT (go-fft/fft#132: 45 of 103 ns at 64 points, 750 of 1,300 ns at
1,024) and a stride-2 deinterleave plus a lane reversal is what the
auto-vectoriser does not do. The float32 forms keep the data float32 and the
arithmetic float64 (go-fft's `DCTMixed`/`MDCTMixed`) with the conversion fused in.
The contract is a bound, not bit identity (`TestCMulGatherBound`,
`TestCMulScatterBound` against a 200-bit computation, every even size from 2 to
2,048): each output within 4 units of the last place of its two products'
magnitudes of the exact value, plus half a float32 ulp for a float32 output. arm64
NEON (`VLD2`/`VST2`, `VEXT`, `VFMUL`, `VFMLS`/`VFMLA`, `VFCVTL`/`VFCVTN`; two complex
numbers per step), generated by go-asmgen (`twiddle_arm64_gen.go`); the portable
loops elsewhere (an AVX2 kernel is not written yet). On an Apple M4 Max, 1,024
points (512 complex numbers): `CMulGather` 533 to 219 ns and `CMulScatter` 538 to 214 ns
against the portable loop (2.4x and 2.5x); 64 points 33 to 18 and 33 to 14 ns.

### Elementwise `Add`, `Sub`, `Div`, `Sqrt`, `ClampScalar` (float64)

| function | computes |
|---|---|
| `Add(dst, a, b)` / `Sub(dst, a, b)` / `Div(dst, a, b)` | `dst[i] = a[i] + b[i]` / `a[i] - b[i]` / `a[i] / b[i]` |
| `Sqrt(dst, src)` | `dst[i] = math.Sqrt(src[i])` |
| `ClampScalar(dst, v, lo, hi)` | `dst[i] = min(max(v[i], lo), hi)` with `Clamp`'s exact NaN and signed-zero rules, scalar bounds (`np.clip(v, lo, hi)`) |

The float64 elementwise kernels go-ndarray kept privately (K1 of the go-scikit
[performance campaign](https://github.com/go-scikit/roadmap/blob/main/docs/performance-campaign.md):
a kernel lives once, in the lowest library every user can import). Each element
is one IEEE operation or a comparison, never a fused instruction, so the results
are **bit-identical to the scalar Go loop and to NumPy on every architecture**
(`np.add`, `np.subtract`, `np.divide`, `np.sqrt`, `np.clip`). amd64 (AVX2, the
usual gate) runs `VADDPD`/`VSUBPD`/`VDIVPD`/`VSQRTPD`, arm64 NEON
`VFADD`/`VFSUB`/`VFDIV`/`VFSQRT`, both ×4 unrolled and generated by go-asmgen
(`binop_*_gen.go`). An amd64 CPU without AVX2+FMA runs SSE2 kernels (`ADDPD`,
`SUBPD`, `MULPD`, `DIVPD`, `SQRTPD`, `MAXPD`/`MINPD` for `ClampScalar`; SSE2 is the
amd64 baseline, no feature test; `sse2_amd64_gen.go`), also bit-identical; CI
forces that path on its AVX2 hosts (`TestSSE2ForcedPath`). ppc64le (VSX),
loong64 (LASX, gated on the CPU), riscv64 (RVV 1.0, gated) and s390x (the z13
vector facility) run `XVADDDP`/`XVADDD`/`VFADDVV`/`VFADB` and their siblings
(`lanes_<arch>_gen.go`; on a native IBM z17, Add and Mul are 2.2x the compiler
loops, Div, Sqrt and `SumPairwise` 1.0-1.1x, never slower); the remaining
architectures run the portable loops. Like `Mul`
they work on the first `len(a)` elements, panic if another slice is shorter,
allow `dst` to alias an input, never read or write past a slice (guard-page
tests).

### `Exp`, `Log` (float64) and `Float32Exp`, `Float32Log`

| function | computes | parity with NumPy |
|---|---|---|
| `Exp(dst, src)` / `Log(dst, src)` | `exp` / `log` of every `src[i]`, float64, 0.511 / 0.519 ULP (Arm optimized-routines, MIT) | **tolerance** (ULP-bounded, not NumPy's bits) |
| `Float32Exp(dst, src)` / `Float32Log(dst, src)` | the **correctly rounded** float32 `exp` / `log` | correct rounding is the reference: every float32 input rounds as the exact value does (proven over all 2^32 inputs by the env-gated `TestExp32CorrectlyRounded` / `TestLog32CorrectlyRounded`, `NDARRAY_EXHAUSTIVE=1`, a 300-bit reference and a certifier; every 65537th input without it); labelled **tolerance** against NumPy, whose float32 exp/log are not correctly rounded |

Moved here from go-ndarray's `internal/kernels` (K1 of the go-scikit
[performance campaign](https://github.com/go-scikit/roadmap/blob/main/docs/performance-campaign.md)),
with the kernels written there: the AVX2 float32 exp/log (go-ndarray#94), the AVX2
float64 log (go-ndarray#96) and the NEON float32 exp/log (go-ndarray#95). The
float32 functions compute in float64 and round once: `expCR` is Arm's correctly
rounded `expf` (optimized-routines, MIT; `math.FMA` exactly where `cr_expf`
fuses) and `logCR` is CORE-MATH's correctly rounded `logf` (MIT; every product
wrapped in `float64(...)` so no architecture fuses it). **Bit-identity to those
Go transcriptions is the oracle**: the AVX2 (amd64) and NEON (arm64) kernels run
the same operations in the same order, and a block of 8 holding a lane they do not
finish (a NaN or |x| > 512 for exp; a non-positive-normal input or bounds that
round apart for log) is not stored, it is handed back to Go. Float64 `Log` has an
AVX2 kernel (blocks of 4, handed back likewise) on amd64; float64 `Exp` and `Log`
on arm64 and every other architecture, and the float32 functions on the other
four, run the Go loops. The NEON kernels use instructions Go's assembler spells
only as `WORD` in go-asmgen's output (FCVTL/FCVTN, UXTL/SXTL, SCVTF, FACGE, CMGT,
BIC); `go tool objdump` on the test binary shows each disassembling to the
mnemonic its comment claims. Nothing allocates. Timing against NumPy is deferred
(`bench/perf`).

### Unfused, NumPy-exact updates (float64)

| function | computes (NumPy expression) |
|---|---|
| `AxpyNoFMA(alpha, x, y)` | `y[i] = y[i] + alpha*x[i]` (`y + alpha*x`) |
| `XpbyNoFMA(x, beta, y)` | `y[i] = x[i] + beta*y[i]` (`x + beta*y`) |
| `Axpby3NoFMA(dst, alpha, a, beta, b, gamma, c)` | `dst[i] = alpha*a[i] + beta*b[i] + gamma*c[i]`, left to right |
| `AxpyRowsNoFMA(a, x, ldx, y)` | `y[j] = (((y[j] + a[0]*x[j]) + a[1]*x[ldx+j]) + …)`, unfused, rows in increasing order: the bits of `len(a)` `AxpyNoFMA` calls with `y` loaded and stored once — one row of an exact matrix product (2.1× the `AxpyNoFMA` loop at 100×100, M4 Max) |
| `AxpyDiffNoFMA(dst, a, f, b, c)` | `dst[i] = a[i] + f*(b[i] - c[i])` — the differential-evolution mutation (rand/1, best/1; `dst = a = c = b` gives `b += f*(x - b)` of rand-to-best/1) |
| `Polyval(dst, x, c)` | `dst[i] = polyval(x[i], c)`, `numpy.polynomial.polynomial.polyval(x, c, tensor=False)`: `c0 = c[-1] + x*0; c0 = c[-i] + c0*x` |
| `Chebval(dst, x, c)` | `dst[i] = chebval(x[i], c)`, `numpy.polynomial.chebyshev.chebval(x, c, tensor=False)`: Clenshaw, `x2 = 2*x`, `c0 = c[-i] - c1; c1 = tmp + c1*x2`, then `c0 + c1*x` |

`Axpy`, `Xpby` and `Axpby3` are **fused**: one rounding per element, which is the
more accurate result and what BLAS does, but not what NumPy does. NumPy never
fuses: `y + alpha*x` is two ufunc calls, a multiply that rounds into a temporary
and an add that rounds again, and `a + F*(b - c)` is three. A solver validated by
exact equality against SciPy (differential evolution, basin hopping) has to take
that path, so these kernels round **every product and every sum on its own, in the
order NumPy evaluates the temporaries**, and are bit-identical to the NumPy
expression on every architecture (the payload of a NaN that an operation itself
creates, `Inf - Inf` or `0*Inf`, aside; a NaN that is the only NaN operand keeps
its sign and payload, as in NumPy).

amd64 (AVX2, same gate as the other kernels) uses `VMULPD`/`VADDPD`/`VSUBPD` and
arm64 `VFMUL`/`VFADD`/`VFSUB` — never a fused instruction; both are ×4 unrolled
with a 1-vector loop and a scalar tail, never read or write past a slice (guard
page tests), and allow `dst` to be the very slice of an input. The portable code
(`ppc64le`, `s390x`, `riscv64`, `loong64`, 32-bit) writes every product through an
explicit `float64(...)` conversion, which the Go specification says prevents the
compiler from fusing `x*y + z`; without it a plain Go loop is *not* NumPy's
arithmetic on those architectures (nor on arm64).

Validated against NumPy 2.5.4 on 13 088 committed fixture cases (the inputs are
regenerated from seeds, the fixture holds a SHA-256 prefix of NumPy's result bits
per case): the four kernels × ten input families (uniform, wide exponent,
cancellation in `b - c`, rounding ties, ±0, `-0` only, `+Inf`, one NaN, ±Inf / NaN of
both signs / ±0) × every length 0..300 and the block boundaries, plus 1e3 / 4097 /
100 001 — 0 mismatches on arm64 and on amd64, from the same fixture. A planted
**fused** variant (`math.FMA`) differs from the fixture in 1 400 to 1 800 cases per
operation, and planted **reordered** variants (`a + (F*b - F*c)`, right-to-left
sums) in 700 to 2 800, so the fixture can tell them apart. Regenerate with
`NOFMA_REGEN=1 go test -run RegenerateNoFMA .` (needs `uv`, or `NUMPY_PYTHON`).
`FuzzNoFMAKernels` checks the SIMD kernels against the portable loops.

### Reproducing `np.sum`: `SumPairwise` (float64)

| function | computes |
|---|---|
| `SumPairwise(a)` | `Σ a[i]`, **bit-identical to `np.sum(a)`** for a contiguous 1-D float64 array; `+0` for an empty slice |

`Sum` adds in the lane order of the SIMD kernels, which is fast but is not
NumPy's order, so its last bits differ from `np.sum`. When a result must be
reproducible against NumPy (a stopping test comparing `np.std` of a population
with a tolerance, a regression against a NumPy oracle), use `SumPairwise`. It is
NumPy's pairwise summation, transcribed from `DOUBLE_pairwise_sum`
(`numpy/_core/src/umath/loops_utils.h.src`, v2.5.3): fewer than 8 elements are added
left to right from `-0`; up to `PW_BLOCKSIZE` = 128 elements are summed with
eight independent accumulators, folded as
`((r0+r1)+(r2+r3)) + ((r4+r5)+(r6+r7))`, then the non-multiple-of-8 rest is
added one by one; a longer block is split at `n/2` rounded down to a multiple of
8 and the two halves are added. `np.add.reduce` then adds the result to its
initial `+0`, so a slice holding only `-0` sums to `+0`, as in NumPy.

It is **bit-identical on every architecture**: the order is fixed in the code,
not by the width of a vector register, and no step is a fused multiply-add.
**The 8..128-element blocks run in SIMD** on amd64 (AVX2: the eight accumulators
`r[0..7]` are two 4-lane YMM registers, `VADDPD` per step, the fold
`((r0+r1)+(r2+r3)) + ((r4+r5)+(r6+r7))` by `VHADDPD` + `VEXTRACTF128` + `VADDSD`) and
arm64 (NEON: four 2-lane registers, `VFADD` per step, the fold by `VFADDP`),
and on ppc64le (VSX), loong64 (LASX), riscv64 (RVV, one `vl=8` group) and s390x
(VX), with the same accumulator-per-lane structure:
every lane receives exactly the additions NumPy's scalar code performs on its
`r[j]`, so the bits do not change. The recursion, the `n < 8` start from `-0`,
the `n % 8` tail and the initial `+0` stay as above; the other architectures run
the portable Go block, which is also the reference the tests compare the SIMD
blocks against (`TestSumPairwiseSIMDMatchesReference`, every length 0..700 at
eight start offsets, on raw bit patterns).

Validated against NumPy 2.5.4 on 6 990 committed fixture cases: every length
0..300 for nine value families (uniform, wide exponent, cancellation, ties at
the rounding edge, ±0, `-0` only, `+Inf`, one NaN of either sign, a mix of
±Inf / NaN / ±0), both sides of every block boundary `128·2^j ± 12` up to
`j = 13`, and 1e5 / 1e6 / 2^20 with odd lengths around them — 0 mismatches.
A NaN result is compared bit for bit when exactly one NaN enters the sum; with
several NaNs (or `+Inf` and `-Inf`) which NaN comes out is hardware-dependent
(in NumPy as here), so only "is NaN" is compared. The fixtures are regenerated
with `SUMPW_REGEN=1 go test -run Regenerate .` (needs `uv`); `FuzzSumPairwise`
checks against an independent index-based transcription.

## Why this library

The Go SIMD-float landscape, compared:

| | dot/dist/cosine | float32 | amd64 | arm64 | ppc64le / s390x / riscv64 / loong64 |
|---|---|---|---|---|---|
| gonum/floats | dot, L2 only | ✗ (float64 only) | SSE | ✗ | ✗ |
| viterin/vek | ✓ | ✓ | AVX2+FMA | ✗ | ✗ |
| kelindar/simd | ✗ (sum/min/max only) | ✓ | AVX2 | NEON | ✗ |

This is the only pure-Go float reduction library that ships the full
vector-search API (dot / Euclidean / cosine) for **both** float32 and float64 on
**all six** of Go's 64-bit SIMD architectures.

## How the SIMD is built

Every kernel is an FMA-based vectorised reduction: a multi-lane accumulator folded
with a fused multiply-add at the vector stride, then a horizontal reduce and a
scalar tail.

| arch | ISA | FMA op | notes |
|---|---|---|---|
| amd64   | AVX2 + FMA3 | `VFMADD231P{S,D}` | runtime-gated on `cpu.X86.HasAVX2 && HasFMA`; scalar fallback otherwise |
| arm64   | NEON | `VFMLA` | 4 accumulators, ×4 unroll for ILP; baseline, no gate |
| riscv64 | RVV | `VFMUL`+`VFREDOSUMVS` | length-agnostic `VSETVLI` stripmining; gated on `cpu.RISCV64.HasV` |
| s390x   | vector facility (**big-endian**) | `VFMADB` | `Sum`/`SumSqDiff` vectorised; float32 uses the scalar reference (no `.SB` ops in the assembler); z13 baseline, no gate. **float64 `Dot` has no VX kernel** — on real z15 the `VFMADB` dot kernel measured 0.56× the gc-autovectorized scalar loop (11.6 vs 20.6 GB/s), so `Dot` routes to that loop instead (see below) |
| ppc64le | VSX (**float32 only**) | `XVMADDASP` | the XV* ops are `WORD`-encoded (not in the released assembler); gated on `cpu.PPC64.IsPOWER9` (the SP ops are ISA-3.0). **float64 has no VSX kernel** — on real POWER9 the gc-autovectorized scalar loop beats it (see below), so float64 routes to that loop |
| loong64 | LSX (**float32 only**) | `vfmadd.s` | `vfmadd.s` is `WORD`-encoded (no Go mnemonic yet); add/sub/xor use `VADDF`/`VSUBF`/`VXORV`. float64 routes to the gc-autovectorized loop. LA464 baseline, no gate |

The `.s` files are committed; regenerate with `go run *_gen.go` (the generators
are build-tagged `//go:build ignore`). All six are validated in CI — amd64/arm64
natively, the other four under QEMU (`tonistiigi/binfmt`) — at **100 % test
coverage**, with differential tests and `FuzzDot`/`FuzzDistance`/`FuzzAxpy`
against the scalar reference on every architecture. The elementwise kernels are
also checked bit for bit against `math.FMA` for every length 0..257 at four
element offsets, and run on slices placed right against `PROT_NONE` guard pages
so that a vector load past either end would fault.

## Floating-point determinism

A SIMD reduction does not add its terms left-to-right: it keeps several
independent accumulator lanes (for instruction-level parallelism) and folds them
at the end, so its rounding differs from a naïve scalar loop. For dot / distance
/ cosine, bit-exactness against a naïve loop is neither meaningful nor required —
correctness to a few ULP is.

So the reference the tests and fuzzers check against (`dotLanes`, `sumSqDiffLanes`,
…) reduces in the **same lane-blocked order** the kernels use, and each kernel is
required to match it to a tight, documented relative tolerance (`1e-12` for
float64, `1e-5` for float32) on **every** architecture. The differential tests
and fuzzers enforce this, making the results deterministic and consistent across
arches.

## Performance

Apple M-series (arm64, native), `go test -bench`, ns/op (lower is better);
*simd* is this library, *naive* is the textbook left-to-right Go loop (which the
Go compiler already turns into a pipelined scalar `FMADD` loop):

| op | n=8 | n=64 | n=512 | n=4096 |
|---|---|---|---|---|
| `Dot` float64 simd  | 7.6 | 14.3 | **71.7** | **539** |
| `Dot` float64 naive | 2.4 | 18.5 | 152 | 1075 |
| `Float32Dot` simd   | 9.5 | 11.7 | 39.4 | 276 |

The SIMD dot product is ~2× the compiler's scalar loop on medium/large vectors
(≈57 GB/s float64, ≈59 GB/s float32 at n=512), and loses only on tiny inputs
(n≤8) where the unroll/setup overhead dominates — the regime where you would not
reach for SIMD anyway.

**Honesty note on the other arches.** amd64's AVX2+FMA kernel is validated for
*correctness* on real x86 (an AVX2/FMA-capable VM) but the native-hardware
*throughput* numbers are pending (the CI/dev x86 runner used here is
TCG-emulated, so its timings are not representative). riscv64 and loong64
are **QEMU-validated for correctness**; native-hardware performance numbers are
pending access to that hardware. s390x is now measured on real z15 (below).

**ppc64le — measured on real POWER9** (GCC Compile Farm cfarm433, go1.26.4,
2026-06-27, `Dot` throughput MB/s, higher is better):

| n | float64 (autovectorized) | float64 if it used VSX | float32 VSX | float32 naive |
|---|---|---|---|---|
| 8    | 5700 | 2520 | 1755 | 2100 |
| 512  | 8700 | 6200 | 6340 | 4100 |
| 4096 | 9030 | 6200 | 6650 | 4150 |

For **float64**, the gc compiler already autovectorizes the plain reduction loop,
and on POWER9 that beats the VSX kernel (VSX was ~0.82× at n≥512), so per this
library's dispatch principle — never run a SIMD kernel where it loses to the
scalar/autovectorized path — there is no float64 VSX kernel on ppc64le; the
reductions route to the autovectorizable loop instead. For **float32**, VSX wins
(~1.55–1.61× over naive for n≥64), so the float32 kernel is kept (POWER9-gated).
Correctness on ppc64le is validated under QEMU *and* on real POWER9 silicon.

**s390x (IBM z15, VXE2, measured 2026-07-03)** — linux1, go1.26.4, `-count=6`,
`Dot` throughput GB/s, higher is better. For **float64** `Dot`, the gc compiler
already autovectorizes the plain reduction loop, and on z15 that beats the
`VFMADB` VX kernel (VX **11.6 GB/s** vs the autovectorized loop's **20.6 GB/s**
= **0.56×**). Per this library's dispatch principle — never run a SIMD kernel
where it loses to the scalar/autovectorized path — there is no float64 `Dot` VX
kernel on s390x; `Dot` routes to the autovectorizable loop instead, so it now
runs at **1.00× parity (20.6 GB/s)** rather than the pre-fix 0.56× loss. `Sum`
and `SumSqDiff` keep their `VFMADB` VX kernels (not measured as losses on z15),
and `Distance`/`CosineSimilarity` build on those and are unchanged; float32 uses
the lane-blocked scalar reference as before. Correctness on s390x is validated
under QEMU *and* on real z15 silicon.

## Changes in v0.15.0

- `Float32Max` and `Float32Min` run AVX2 kernels on amd64 from 32 elements up,
  behind the same `AVX2+FMA` gate as the other AVX2 kernels; the SSE2 kernels of
  v0.14.0 stay as the fallback (and below 32 elements). Contract unchanged
  (floats#46). One Zen 3 core (AMD EPYC 7773X), n = 1048576: 87.6 -> 67 us (Max),
  90 -> 65 us (Min); n = 16384: 1.40 -> 0.77 us and 1.32 -> 0.74 us.

## Changes in v0.14.0

- `Float32Max` and `Float32Min` run SIMD kernels, moved here from go-ndarray's
  `internal/kernels` so the kernel lives once (go-ndarray/ndarray#98): SSE2
  (amd64, baseline), NEON (arm64, from 16 elements), LSX (loong64, gated on
  LASX), VSX (ppc64le, gated on POWER8+), RVV (riscv64, gated on V) and VXE
  (s390x, z14+, from 16 elements); every other target, and every CPU without the
  extension, runs a four-chain loop. The contract is unchanged and bit-for-bit
  the sequential loop's (and `numpy.max`/`numpy.min`'s): NaN if any element is
  NaN, `-0` below `+0`, a panic on an empty slice. Tests: NaN and zeros at every
  position of every length up to 100 (every lane and tail slot), `PROT_NONE`
  fences on amd64 and arm64, a CPU-gate-off rerun on the four QEMU targets, and
  `FuzzExtrema32` (nightly in `fuzz.yml`, seed corpus in CI).
- The s390x CI lane runs QEMU's `max` CPU model (the float32 kernels need z14).

## Changes in v0.12.0

- `Polyval(dst, x, c)` and `Chebval(dst, x, c)`: Horner and Clenshaw evaluation

  (`polynomial/polynomial.py` `polyval`, `polynomial/chebyshev.py` `chebval`),
  unfused, bit-identical to NumPy's result (fixtures built in a linux/amd64

  loong64 and the 32-bit targets run the portable loop (#30).

## Changes in v0.10.0

- `Max`, `Min`, `Float32Max`, `Float32Min` order `-0 < +0` like NumPy and Go's
  `max`/`min` (#32).
- amd64 CPUs without AVX2+FMA run SSE2 kernels for `Add`, `Sub`, `Mul`, `Div`,
  `Sqrt`, `ClampScalar` (#31).
- ppc64le, loong64, riscv64 and s390x run the `SumPairwise` block and the
