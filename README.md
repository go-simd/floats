# floats

[![CI](https://github.com/go-simd/floats/actions/workflows/ci.yml/badge.svg)](https://github.com/go-simd/floats/actions/workflows/ci.yml)
![coverage](https://img.shields.io/badge/coverage-100%25-brightgreen)
[![Go Reference](https://pkg.go.dev/badge/github.com/go-simd/floats.svg)](https://pkg.go.dev/github.com/go-simd/floats)

SIMD-accelerated reductions over `[]float32` and `[]float64` — the dot product,
sum, min, max, Euclidean (L2) distance and cosine similarity that sit at the
heart of **vector search, embeddings and numerics**, plus the float64
`Axpy`/`Xpby`/`AxpyDot`/`Scale` updates behind iterative solvers and the
`Mul`/`Axpby3`/`Clamp`/`MaxAbs` kernels of splitting QP solvers, and the
NumPy-exact `SumPairwise` and unfused `AxpyNoFMA`/`AxpyDiffNoFMA`/… kernels
(bit-identical to `np.sum` and to `a + F*(b - c)`). Pure Go: `CGO_ENABLED=0`,
stable Go, no `GOEXPERIMENT`. The hot reduction loops are real FMA SIMD on **all
six 64-bit Go targets**, assembly generated by
[go-asmgen](https://github.com/go-asmgen/asmgen) — on a plain `go build`.

```go
import "github.com/go-simd/floats"

sim := floats.CosineSimilarity(query, doc)        // []float64 relevance score
d   := floats.Float32Distance(embA, embB)         // []float32 L2 distance
dp  := floats.Dot(a, b)                            // a·b
```

## API

For `[]float64` (top-level) and `[]float32` (the `Float32*` functions):

| float64 | float32 | meaning |
|---|---|---|
| `Dot(a, b)`              | `Float32Dot(a, b)`              | a·b = Σ aᵢbᵢ |
| `Sum(a)`                 | `Float32Sum(a)`                 | Σ aᵢ |
| `Min(a)` / `Max(a)`      | `Float32Min(a)` / `Float32Max(a)` | min / max element (NaN-propagating; `-0 < +0` as NumPy: max of a mix with a `+0` is `+0`, min of a mix with a `-0` is `-0`) |
| `Distance(a, b)`         | `Float32Distance(a, b)`         | ‖a−b‖₂ = √Σ(aᵢ−bᵢ)² |
| `CosineSimilarity(a, b)` | `Float32CosineSimilarity(a, b)` | a·b / (‖a‖₂‖b‖₂) |

`Dot`, `Distance` and `CosineSimilarity` require `len(a) == len(b)` and panic
otherwise; `Min`/`Max` panic on an empty slice; `Sum` of an empty slice is 0.
The float32 dot/sum/squared-difference are accumulated in float32; cosine and
distance take the final square root in float64 for accuracy.

### Elementwise updates (BLAS level 1, float64)

The in-place updates that iterative solvers (CG, GMRES), Householder QR and LU
elimination spend their time in:

| function | computes |
|---|---|
| `Axpy(alpha, x, y)`       | `y[i] = math.FMA(alpha, x[i], y[i])` (y += αx) |
| `Xpby(x, beta, y)`        | `y[i] = math.FMA(beta, y[i], x[i])` (y = x + βy) |
| `AxpyDot(alpha, x, y, w)` | Axpy, then returns Σ `y[i]*w[i]` over the updated y, in one pass |
| `Scale(alpha, x)`         | `x[i] *= alpha` |

```go
// one conjugate-gradient step
floats.Axpy(alpha, p, x)              // x += αp
rr := floats.AxpyDot(-alpha, ap, r, r) // r -= αAp, rr = r·r
floats.Xpby(r, rr/rrOld, p)            // p = r + βp
```

They operate on the first `len(x)` elements and panic if `y` (or `w`) is
shorter. `y` may be the same slice as `x` or `w`; partially overlapping slices
are not supported.

**Bit-identical on every architecture.** Each updated element is rounded once,
exactly as `math.FMA` rounds it: `VFMADD` on amd64 (AVX2+FMA), `VFMLA`/`FMADDD`
on arm64, the `math.FMA` loop everywhere else (one hardware FMA instruction on
ppc64le, s390x, riscv64 and loong64). The updated slice never depends on the
architecture or the CPU features detected at run time (NaN payloads aside).
This is *not* the unfused `y[i] + alpha*x[i]` that amd64 Go code computes, so
replacing such a loop can change the last bit; the fused result is the more
accurate one. `AxpyDot`'s returned sum is a reduction and follows the
lane-order rules of [Floating-point determinism](#floating-point-determinism).

| arch | elementwise kernel |
|---|---|
| amd64 | AVX2+FMA, ×4 unrolled (16 elements/iteration), gated on `HasAVX2 && HasFMA` |
| arm64 | NEON, ×4 unrolled (8 elements/iteration, four-register `VLD1`/`VST1`) |
| ppc64le, s390x, riscv64, loong64 | portable `math.FMA` loop: no kernel until one is measured on the real silicon, as for the reductions |

### Gather kernels (index list, float64)

The free-set operations of bound-constrained solvers (L-BFGS-B subspace
minimisation, active-set QP): vectors read through a list of active indices.

| function | computes |
|---|---|
| `DotIdx(a, b, idx)`          | Σₖ `a[idx[k]]*b[idx[k]]` |
| `DotGather(a, idx, d)`       | Σₖ `a[idx[k]]*d[k]` (`d` contiguous, `a` gathered) |
| `AxpyGather(alpha, a, idx, d)` | `d[k] = math.FMA(alpha, a[idx[k]], d[k])` for every k |

They are portable Go (no assembly yet; a SIMD gather can replace them behind
the same signatures). They panic if an index is out of range or
`len(d) < len(idx)`. Repeated and unordered indices are allowed.

**Accuracy contract.** The two sums use four FMA accumulators over
lane-blocked groups of four indices (`k mod 4`), combined as
`(s0+s1)+(s2+s3)`: they are **not** summed left to right, so the last bit
differs from the obvious loop. The stated bound, asserted against a 300-bit
`math/big` oracle, is |result − exact| ≤ n·ε·Σₖ|aᵢbᵢ| with ε = 2⁻⁵² (plus an
absolute 2⁻¹⁰⁷⁴ term per element when products underflow to subnormals).
`AxpyGather` rounds each element once and is bit-identical everywhere.

### Products, combinations, clamping, infinity norm (float64)

The vector kernels of splitting solvers (ADMM / OSQP-style quadratic
programming): the product with a diagonal, the three-term update, the projection
onto a box and the ∞-norm of a residual.

| function | computes |
|---|---|
| `Mul(dst, a, b)`                              | `dst[i] = a[i]*b[i]` |
| `Axpby3(dst, alpha, a, beta, b, gamma, c)`    | `dst[i] = math.FMA(gamma, c[i], math.FMA(beta, b[i], alpha*a[i]))` (αa + βb + γc, fused) |
| `Clamp(dst, v, lo, hi)`                       | `dst[i] = min(max(v[i], lo[i]), hi[i])`, with the exact NaN and signed-zero rules below |
| `MaxAbs(v)`                                   | the largest `abs(v[i])` (the ∞-norm); 0 for an empty slice |
| `MaxAbsMul(v, w)`                             | `max(abs(v[i])*w[i])`, the weighted max-norm of ODE error control, folded with C's `fmax` from +0 (a NaN product loses), bit-identical to that loop; NEON on arm64, AVX2 on amd64, portable loop elsewhere; 0.17–0.43 of NumPy's time (arm64, one core) |

```go
// one ADMM-style step: z = Π_[l,u](α·Ax + (1−α)·z_prev + y/ρ)
floats.Axpby3(t, alpha, ax, 1-alpha, zPrev, 1, yOverRho)
floats.Clamp(z, t, l, u)
rNorm := floats.MaxAbs(r)
```

Like the updates above they work on the first `len(a)` (`len(v)`) elements,
panic if another slice is shorter, and allow `dst` to be the same slice as an
input. All four are **bit-identical on every architecture**: `Mul` is one IEEE
multiply per element; `Axpby3` **is fused** — two `math.FMA` steps after the
rounded product `alpha*a[i]`, so it differs from the unfused
`alpha*a[i] + beta*b[i] + gamma*c[i]` by at most a few ULP of `Σ|terms|` (the
tests check that tolerance and also that the fused form is what runs); `Clamp`
and `MaxAbs` round nothing.

`Clamp` is `r := v[i]; if lo[i] > r { r = lo[i] }; if hi[i] < r { r = hi[i] }`:
a NaN `v[i]` comes out unchanged (same bits, either sign); a NaN bound is ignored
(that side is unbounded); `lo[i] > hi[i]` gives `hi[i]`; signed zeros compare
equal, so the result is `v[i]` unless a strict bound replaces it. `MaxAbs`
returns `math.NaN()` if any element is NaN (either sign, quiet or signaling) and
`+Inf` if there is an infinity and no NaN; an all-zero slice gives `+0`.

| arch | kernels |
|---|---|
| amd64 | AVX2+FMA, ×4 unrolled (`VMULPD`, `VFMADD231PD`, `VMAXPD`/`VMINPD` with the operand order that gives the strict compare, `VANDPD` + `VMAXPD` + an unordered-compare NaN mask), same `HasAVX2 && HasFMA` gate |
| arm64 | NEON, ×4 unrolled (`VFMUL`, `VFMLA`, `VFCMGT` + `VBIT` — not `FMAX`/`FMIN`, which treat NaN bounds and signed zeros differently —, `VFABS` + `VFMAX`) |
| ppc64le, s390x, riscv64, loong64 | the portable loops, as for the updates above (`Mul` has a kernel there, see below) |

### `OverlapWindow`, `Float32OverlapWindow`: windowed overlap-add of lapped transforms

| function | computes (n = len(a), j = n-1-i) |
|---|---|
| `OverlapWindow(dst, a, b, win)` / `Float32OverlapWindow(...)` | `dst[i] = a[i]*win[2n-1-i] - b[j]*win[i]`, `dst[2n-1-i] = a[i]*win[i] + b[j]*win[2n-1-i]` for `i < n` |

The inner loop of the synthesis of every MDCT codec (AAC, Vorbis, Opus CELT, AC-3,
MP3): the second half of the previous block and the first half of this one are
combined under a window, so that the time-domain aliasing cancels. `b`, `win` and
`dst` are read and written from both ends, which the auto-vectoriser cannot do; the
kernels reverse a register instead. The contract is a bound, not bit identity: each
output is within 2 units of the last place of its two products' magnitudes of the
exact value (`TestOverlapWindowBound` against a 200-bit computation, float32 and
float64, every size from 1 to 1024). arm64 NEON (`VREV64`+`VEXT`, `VFMUL`,
`VFMLS`/`VFMLA`; 4 float32 or 2 float64 lanes) and amd64 AVX2+FMA (`VPERMILPS` +
`VPERM2F128` or `VPERMPD`, `VFNMADD231`/`VFMADD231`; 8 or 4 lanes), generated by
go-asmgen (`overlap_*_gen.go`); the portable loop elsewhere and on an amd64 CPU
without AVX2+FMA. On an Apple M4 Max, 1024 steps: float32 764 to 212 ns (3.6x),
float64 789 to 377 ns (2.1x) against the portable loop. Wanted by go-avkit/decode
(AAC) and go-fft's TDAC helper.

### `CMulGather`, `CMulScatter`: the twiddle passes of the DCT-IV and the MDCT

| function | computes (n = len(tw), a complex number is two consecutive float64) |
|---|---|
| `CMulGather(dst, x, tw)` | for `m < n/2`: `dst[2m] = x[2m]*tw[2m] - x[n-1-2m]*tw[2m+1]`, `dst[2m+1] = x[2m]*tw[2m+1] + x[n-1-2m]*tw[2m]` |
| `CMulScatter(dst, c, tw, f)` | `z = tw[m]*c[m]` (complex), `dst[2m] = f*Re z`, `dst[n-1-2m] = -f*Im z` |
| `CMulGatherFrom32(dst, x, tw)` | `CMulGather` with `x` float32, widened in the kernel |
| `CMulScatterTo32(dst, c, tw, f)` | `CMulScatter` with `dst` float32, each output rounded once |

A DCT-IV of even length is an n/2-point complex FFT between two passes over the
data: the real input is read as complex pairs of its even samples and its odd
samples from the end, multiplied by a table; the FFT's output is multiplied by a
table and written back, real parts to the even positions and negated imaginary
parts to the odd ones from the end. Those passes are more than half of a small
DCT-IV or MDCT (go-fft/fft#132: 45 of 103 ns at 64 points, 750 of 1,300 ns at
1,024) and a stride-2 deinterleave plus a lane reversal is what the
auto-vectoriser does not do. The float32 forms keep the data float32 and the
arithmetic float64 (go-fft's `DCTMixed`/`MDCTMixed`) with the conversion fused in.
The contract is a bound, not bit identity (`TestCMulGatherBound`,
`TestCMulScatterBound` against a 200-bit computation, every even size from 2 to
2,048): each output within 4 units of the last place of its two products'
magnitudes of the exact value, plus half a float32 ulp for a float32 output. arm64
NEON (`VLD1`+`VUZP`, `VZIP`+`VST1`, `VEXT`, `VFMLS`/`VFMLA`, `VFCVTL`/`VFCVTN`; two
complex numbers per step) and amd64 AVX2+FMA (`VSHUFPD`+`VPERMPD`, `VUNPCK`+
`VPERM2F128`, `VFNMADD231PD`/`VFMADD231PD`, `VCVTPS2PD`/`VCVTPD2PS`; four complex
numbers per step), generated by go-asmgen (`twiddle_*_gen.go`); the portable loops
elsewhere and on an amd64 CPU without AVX2+FMA. On an Apple M4 Max, 1,024
points (512 complex numbers): `CMulGather` 533 to 219 ns and `CMulScatter` 538 to 214 ns
against the portable loop (2.4x and 2.5x); 64 points 33 to 18 and 33 to 14 ns.

### `MDCTFold`, `MDCTUnfold`: the fold and unfold of the MDCT and the IMDCT

| function | computes (N = len(x), m = N/2, h = N/4, i < h) |
|---|---|
| `MDCTFold(dst, x)` | `dst[i] = -(x[m+h-1-i] + x[m+h+i])`, `dst[h+i] = x[i] - x[m-1-i]` |
| `MDCTUnfold(dst, u)` | `dst[i] = u[h+i]`, `dst[m-1-i] = -u[h+i]`, `dst[m+h-1-i] = -u[i]`, `dst[m+h+i] = -u[i]` (m = len(u)) |
| `MDCTFoldFrom32(dst, x)` | the fold with `x` float32, widened (the sum is float64) |
| `MDCTUnfoldTo32(dst, u)` | the unfold with each output rounded to float32 |

An MDCT is a DCT-IV on a folded copy of the block, an IMDCT a DCT-IV followed by the
inverse arrangement (Wikipedia's fold `(a, b, c, d) -> (-c_r - d, a - b_r)`); every
MDCT codec does both, around the twiddle passes of `CMulGather`/`CMulScatter`. Both
read and write forward and reversed runs of consecutive elements, which the compiler
does not vectorise and a lane reversal does. Each output is one addition, subtraction
or negation, nothing fused, so the kernels equal the portable loops exactly
(`TestMDCTFoldExact` against a 200-bit computation, every block length from 4 to 4,096,
and `FuzzMDCTFold`). `dst` must not overlap its operand, not even exactly: checked,
panics. arm64 NEON (`VLD1`, `VEXT`, `VFADD`/`VFSUB`/`VFNEG`; 2 lanes) and amd64 AVX2
(`VPERMPD $0x1B`, `VADDPD`/`VSUBPD`, an XOR for the sign; 4 lanes), generated by
go-asmgen (`fold_*_gen.go`); the portable loops elsewhere and on an amd64 CPU without
AVX2+FMA. On an Apple M4 Max, a 2,048-sample block: fold 376 to 113 ns (3.3x), unfold
355 to 160 ns (2.2x); 128 samples 23 to 15 ns and 22 to 15 ns (load 9).

### `SquaredMagnitude`: the power pass of a periodogram

`SquaredMagnitude(dst, c, s)` writes `dst[k] = (c[2k]² + c[2k+1]²)·s` for the
`n = len(dst)` complex numbers held as consecutive `(re, im)` pairs in `c`: the last
pass of a PSD, a spectrogram or a power spectrum. A loop in Go reads the pairs with a
stride of two; the kernels deinterleave four (AVX2) or two (NEON) bins per step. The
contract is a bound, not bit identity: the squares and their sum are non-negative, so
every output is within 4 units of the last place of the exact value (the portable loop
rounds four times, a kernel fuses the second square with the sum), asserted by
`TestSquaredMagnitudeBound` against a 200-bit computation at every length from 1 to
70 and at the sizes of a spectrogram, with a fuzz target. `dst` must not overlap `c`,
not even exactly: checked, panics. arm64 NEON (`VUZP1`/`VUZP2`, `VFMUL`, `VFMLA`) and
amd64 AVX2+FMA (`VSHUFPD`+`VPERMPD`, `VFMADD231PD`), generated by go-asmgen
(`sqmag_*_gen.go`); the portable loop elsewhere and on an amd64 CPU without AVX2+FMA.
On an Apple M4 Max, 129 bins (a 256-point real transform): 85 to 25 ns (3.4x); 1,025
bins 654 to 169 ns (3.9x) (load 17). Wanted by go-fft's `PSD` and `Spectrogram`
(go-fft/fft#123).

### `MirrorCombine`, `MirrorCombineSplit`: the pair pass of a real transform

For a spectrum `z` of `n` complex numbers (`(re, im)` pairs), `k = 1 .. n-1`:
`u = z[k] + conj(z[n-k])`, `v = -i (z[k] - conj(z[n-k]))`, `r[k] = w1[k] u + w2[k] v`
(complex products). `MirrorCombine` stores `r[k]` as complex number `k` of `dst`;
`MirrorCombineSplit` stores `dst[k] = Re r[k]` and `dst[2n-k] = -Im r[k]`, the layout of
a DCT-II. It is the post-pass of Makhoul's DCT-II and the pre-pass of the DCT-III (go-fft/fft#162)
and, with other weights, the untangle of a real FFT. Within a bound, not bit for bit (the
kernel fuses the products): 4 eps of `|w1||u| + |w2||v|` against a 300-bit oracle, at
every length from 0 to 130 and at 255, 256, 257, 1000, 4097, with a fuzz target. `dst`
must not overlap an input (checked, panics, nothing written); `len(z)` must be even and
`w1`, `w2`, `dst` at least as long. amd64 AVX2+FMA (`VFMADDSUB231PD`, two values of `k`
per step), generated by go-asmgen (`mirror_amd64_gen.go`); the portable loop elsewhere,
arm64 included (no NEON kernel yet).

### `CMulZipRev`: a mirrored-halves gather with a complex multiply

`CMulZipRev(dst, x, y, w)` writes, for `j < m = len(dst)/2`,
`dst[j] = w[j] * (x[j] - i y[m-1-j])`: the real parts are one contiguous run, the
imaginary parts another read from its end, `w` is a table of `m` complex numbers (pairs).
It is the pre-pass of Makhoul's DCT-III (go-fft/fft#162), before `MirrorCombine`. Within
a bound, not bit for bit (the kernel fuses the products): 4 eps of `|w||(x, y')|` plus an
absolute floor of 64 smallest subnormals, against a 300-bit oracle, at every length from
0 to 130 and at 255, 256, 257, 1000, 4097, with a fuzz target whose corpus entry fails
the bound without the floor. `dst` must not overlap `x`, `y` or `w` (checked, panics,
nothing written). amd64 AVX2+FMA (`VPERMPD` reversal, `VUNPCKLPD/HPD`, `VFMADDSUB231PD`,
four numbers per step), generated by go-asmgen (`cmulziprev_amd64_gen.go`, gated in CI
like `mirror_amd64.s`); the portable loop elsewhere, arm64 included.

### `ConjReverse`: the conjugate mirror of a Hermitian spectrum

`ConjReverse(dst, src)` writes the `n = len(dst)/2` complex numbers held as consecutive
`(re, im)` pairs in `src`, conjugated and in reverse order: `dst[2k] = src[2(n-1-k)]`,
`dst[2k+1] = -src[2(n-1-k)+1]`. It is the mirror `X[N-k] = conj(X[k])` that turns the
`N/2+1` bins of a real transform into the full spectrum. Every output is a copy or a
negation, so the result is exact, not within a bound: `TestConjReverseExact` compares
bits (signed zeros and NaN payloads included) at every length from 0 to 70 and at the
sizes of a transform's mirror, with a fuzz target. `dst` must not overlap `src`, not
even exactly: checked, panics; `len(dst)` must be even. arm64 NEON (four registers of
`VLD1`, `VEOR` with the sign of the imaginary lane, `VST1`) and amd64 AVX2 (`VPERMPD`
half swap, `VXORPD`), generated by go-asmgen (`conjrev_*_gen.go`); the portable loop
elsewhere and on an amd64 CPU without AVX2+FMA. On a Ryzen 9 7950X, 511 numbers (the
mirror of a 1,024-point real transform): 378 to 52 ns (7.2x); 2,047 numbers 1,513 to 385
ns (3.9x). Wanted by go-fft's `FFTReal` (go-fft/fft#122).

### `MulAddRows`: the window sum of a polyphase bank

`MulAddRows(dst, a, lda, b, ldb, rows)` computes `dst[j] += Σ_k a[k*lda+j]*b[k*ldb+j]` for
`k < rows` and `j < len(dst)`: output `j` is a sum of products of two matrices read down a
column, the window stage of an MDCT or QMF synthesis bank (64 columns, 10 rows). A Go loop
over the rows loads and stores the accumulator once per row; the kernel holds a block of
`dst` in registers across all the rows (NEON 16, 4, 2 then 1 column, AVX2 16, 4 then 1),
so `a`, `b` and `dst` are each loaded once. Every term is one fused multiply-add in
increasing `k`, starting from the value `dst[j]` holds, so the result is bit-identical on
every architecture (kernel and `math.FMA` loop do the same operations in the same order,
as `Axpy` does): `TestMulAddRowsExact` compares bits at every column count from 1 to 70
and the sizes of a bank, with padded and zero strides, `TestMulAddRowsAgainstExact` holds
it to `rows+1` units of the last place of the sum of magnitudes against a 300-bit
computation (the measured worst is 2 units for ten rows), plus a fuzz target and guard
pages. `dst` must not overlap the elements of `a` or `b` that are read: checked, panics.
arm64 NEON (`VLD1.P`, `VFMLA`) and amd64 AVX2+FMA (`VFMADD231PD`), generated by go-asmgen
(`mulrows_*_gen.go`); the portable loop elsewhere and on an amd64 CPU without AVX2+FMA.
Wanted by go-avkit/decode's SBR synthesis bank (go-avkit/decode#77).

### `MulAddRows32`: the window sum of a float32 polyphase bank

`MulAddRows32(dst, a, lda, b, ldb, rows)` is `MulAddRows` on `float32` data, eight (AVX2)
or four (NEON) columns to a register: `dst[j] += Σ_k a[k*lda+j]*b[k*ldb+j]`, the block of
`dst` held in registers across all rows. Every term is one fused float32 multiply-add in
increasing `k`, so the stated contract is an error bound, not bit identity with another
code: `|dst[j] - exact| <= rows·2^-24·(|dst0[j]| + Σ|a·b|)·(1 + rows·2^-24)`, asserted
against a `math/big` computation at every shape by `TestMulAddRows32AgainstExact`, plus a
fuzz target, guard pages, and asserted panic messages (`TestMulAddRows32PanicsAndBounds`).
On one Zen 4 core a 64-column, 10-row bank takes 13.7 ns against 23.8 ns for the
`float64` `MulAddRows` on the same shape. `dst` must not overlap the elements read of `a`
or `b`: checked, panics. amd64 AVX2+FMA and arm64 NEON, generated by go-asmgen
(`mulrows32_*_gen.go`); the portable loop elsewhere. Wanted by go-avkit/decode's float32
SBR synthesis bank (go-avkit/decode#77).

### `AllPass3`: the all-pass rows of the Parametric Stereo decorrelator

`AllPass3(out, in, t, old, cur)` computes, for each row `k` of a slot of complex samples,
`x = Phi*in`, then three Schroeder links in series (`p = Q_l*old_l`, `c = x + C_l*p` written
to `cur_l`, `x = p - C_l*c`) and `out = x`: the all-pass half of the HE-AAC v2 decorrelator
(ISO/IEC 14496-3). The rotations and real coefficients are the seven tables of `AllPassRows`;
the caller resolves the ring pointers `old` and `cur`. The kernel does two rows per AVX2
register (one per NEON register) and keeps all three links in registers. Every complex
product is one rounded product and one fused sum, so kernels and the portable `math.FMA`
loop are bit-identical on every architecture; the stated error bound (a few units of
2^-53 times the largest magnitude of the chain, recurrence in the source) is asserted for
`out` and every `cur_l` against a 200-bit `math/big` computation by `TestAllPass3Bound` and
`FuzzAllPass3` (worst measured 0.61 of the bound), plus guard pages and overlap checks
(a written slice overlapping another operand panics). On amd64 (AVX2+FMA, 34 rows) about
2.3x faster than the complex128 Go loop. arm64 NEON and amd64 AVX2+FMA generated by
go-asmgen (`allpass_*_gen.go`). Wanted by go-avkit/decode#77.

`NewAllPass3Plan(t, out, in, inStride, w, wStride)` is the same kernel for a decorrelator that
calls it once per slot: the tables, the output, the input ring and the three link rings are
proved once (lengths, strides, no overlap between written and other memory), and
`plan.Run(inSlot, oldSlot, curSlot)` names the memory by slot numbers, so a call only checks
eight integer ranges (it panics on a slot out of range or a link that reads the slot it
writes). `plan.Out()` is the output. In go-avkit/decode this is about 1.2 % of an HE-AAC v2
decode, where the per-call proof of `AllPass3` cost more than it saved.

### `CDotC`: the conjugated complex dot product

`CDotC(a, b)` returns `Σ conj(a_k)·b_k` (the BLAS `zdotc`) as `(re, im)` for the `n =
len(a)/2` complex numbers held as consecutive `(re, im)` pairs: the lag-k correlation of a
complex sequence with itself, the covariance estimate of a linear predictor (the SBR
inverse-filtering predictor of go-avkit/decode, go-avkit/decode#77). The sum of squared
magnitudes of a complex slice needs no kernel: `Dot(a, a)` over the same float64 view is
`Σ (re² + im²)`. A Go loop is one dependent chain per accumulator; the kernels run a block of
four complex numbers per step with the second sum on the swapped parts of `b` (NEON
`VFMLA` on `VEXT`-swapped registers, AVX2 `VFMADD231PD` on `VPERMILPD`-swapped ones) and
fold the lanes at the end. The contract is a bound, not bit identity: both parts are
reordered and fused, so each is within `(2n+2)·2^-53` (the portable path, one serial chain of
2n fused steps; reached by an adversarial input, so not improvable) or `(n/4+8)·2^-53` (the
vector paths) of the sum of the absolute values of its products of the exact value, asserted
against a 300-bit computation at every length from 0 to 70 complex numbers and at the sizes
of a transform by `TestCDotCBound`, by `TestCDotCAdversarial` (same-sign rounding errors, and
massive cancellation), with a fuzz target and guard pages. `len(a)` must be even and `b` at least as long (panics). amd64 AVX2
tests run on a CI runner and fail, not skip, when AVX2+FMA is missing there
(`TestCDotCAVX2Dispatch`); the portable loop elsewhere and on an amd64 CPU without it.
Measured, 38 complex numbers (one SBR predictor lag): Ryzen 9 7950X 47 to 10.7 ns (4.4x), M4
Max 47 to 18 ns (2.6x).

### `CMulTo`: the pointwise complex product

`CMulTo(dst, a, b []complex128)` writes `dst[i] = a[i]*b[i]` for `i < len(dst)` (NumPy's
`multiply` on complex128): the chirp and spectral products of Bluestein's algorithm, the
filter of a frequency-domain convolution. It panics, before writing anything, if `a` or `b` is
shorter than `dst`; `dst` may be `a` or `b` exactly (in place), any other overlap is
undefined. The AVX2+FMA kernel takes four numbers per step with one multiply and one
`VFMADDSUB231PD` per two numbers (real part `fma(ar, br, -(ai*bi))`), then finishes the last
two and one itself, in one call; the arm64 kernel is the scalar loop in assembly (`FMADDD`,
`FMSUBD`, paired loads and stores, no bounds checks), not NEON, which lost to Go's loop below
64 numbers on Neoverse; the s390x kernel (vector facility, z13 and later) holds one complex
number per register, four per step (`VFMDB`, `VFMADB` on the swapped parts, a sign vector
for the real part), from 20 numbers; the ppc64le kernel (VSX, POWER8 and later, from 32
numbers) splits two numbers into real and imaginary vectors (`XXPERMDI`, `XVMULDP`,
`XVMSUBADP`, `XVMADDADP`, then `XXPERMDI` back), four per step, because the
one-number-per-register form lost to Go's loop by 11 to 30 % on POWER9; other CPUs run
Go's complex product.
The contract is a bound, not bit identity: each part is within 2 eps (2^-52) of `|a|·|b|`
of the exact product, plus 64 smallest subnormals when a product underflows (the fused
and the unfused forms both meet it), asserted against a 300-bit `math/big` oracle by
`TestCMulToOracle`, with in-place, panic-before-write, guard-page, noescape and fuzz tests.
Measured on one core (Zen 4, interleaved, median of 21 rounds, load below 1), against the
scalar Go loop: 5.7 ns against 10.9 at 16 numbers, 13.4 against 39.9 at 64, 295 against 630
at 1024 (1.9x to 3x); against go-fft's former unfused AVX2 kernel it is 0.2 ns faster at 16,
0.5 at 32, 0.8 at 64, 1.4 at 128, 2.6 at 256, 8.5 at 512 and 2 ns (0.7 %) slower at 1024
(memory bound). The v0.32.0 kernel with its Go tail was 6.7 ns at 16. `np.multiply` there
was 772 ns at 1024 numbers (earlier measurement). Neoverse-N2 (GitHub arm64 runner, load
0.3, interleaved): 16.0 ns against 19.9 for the Go loop at 16 numbers (23.1 for the v0.32.0
NEON kernel), 55.8 against 72.5 at 64, 857 against 1135 at 1024. s390x (z17, load 0.0,
interleaved, A/A agrees): 30.1 ns against 40.0 for the Go loop at 32 numbers, 50.0 against
76.4 at 64, 696 against 1157 at 1024 (1.7x); at 16 numbers the loop runs (21.5 against
21.8). POWER8E (cfarm112, one pinned core): 70.2 against 83.5 at 32, 108.6 against 143.8 at
64, 1270 against 1954 at 1024 (1.5x). POWER9 (cfarm29, one pinned core): 58.9 against 70.3
at 32, 107.7 against 117.4 at 64, 1690 against 1753 at 1024 (3.6 %); at 16 numbers the loop
runs on both (the wrapper costs 2.6 ns over the bare loop on POWER9).

allow `dst` to alias an input, never read or write past a slice (guard-page

### Elementwise `Add32`, `Sub32`, `Mul32`, `Div32`, `Sqrt32` (float32)

| function | computes |
|---|---|
| `Add32(dst, a, b)` / `Sub32` / `Mul32` / `Div32` | `dst[i] = a[i] + b[i]` / `a[i] - b[i]` / `a[i] * b[i]` / `a[i] / b[i]` |
| `Sqrt32(dst, src)` | `dst[i] = float32(math.Sqrt(float64(src[i])))` |

The single-precision siblings of `Add`, `Sub`, `Mul`, `Div`, `Sqrt`, wanted by
go-ndarray to delete its private SSE2 copies. Each element is **one IEEE-754
binary32 operation** (the exact correctly rounded result, no fused instruction),
bit-identical to the scalar Go loop and to NumPy's float32 ufuncs, up to the payload
of a NaN an operation itself creates. `Sqrt32` is proved correctly rounded over
**all 2^32 float32 bit patterns** on amd64 and arm64 (`TestSqrt32Exhaustive`,
about 2 s per kernel on a many-core machine, skipped with `-short`) against an
oracle that uses no square root: the result must lie between the neighbouring
midpoints, checked by squaring them exactly in float64. On the emulated
architectures (loong64, ppc64le, riscv64, s390x) the same test checks every
1021st bit pattern (about 4.2 million), plus the specials of `TestSqrt32Specials`.
Like the float64 functions they work on the first `len(a)`
(`len(src)`) elements, panic if another slice is shorter and allow `dst` to alias an
input. amd64: AVX2 (`VADDPS` ..., 32 elements per iteration, the usual gate), SSE2
(`ADDPS` ..., the amd64 baseline) on a CPU without AVX2+FMA; arm64: NEON
(`VFADD` ... on `.S4`, 16 elements per iteration); loong64: LSX (`VFADDS` ...,
gated on LASX like the float64 kernels); ppc64le: VSX (`XVADDSP` ..., POWER8
baseline, gated on `hasVSX`); riscv64: RVV 1.0 (`VFADDVV` ... on 32-bit elements,
strip-mined, any VLEN, gated on V); s390x: vector-enhancements facility 1 (`VFASB`
..., z14 or later, gated on `hasVXE`); on a CPU without the feature, or for an
empty slice, the portable loop. Generated by go-asmgen
(`binop32_<arch>_gen.go`, regenerated and diffed in CI); the portable loops
elsewhere. On amd64, `Add32`, `Sub32` and `Mul32` switch from the AVX2 to the SSE2
kernel from 65536 elements (`binop32SSEFrom`): past the L2 cache the loop is bound by
memory and on Zen 3 (EPYC 7773X) the 128-bit loop is 7-10 % faster (`Add32` n=1e6 165 us
against 181 us); `Div32` is divider-bound and keeps AVX2. Results are bit-identical
either way. The loong64, ppc64le, riscv64 and s390x kernels are unmeasured on
hardware (the QEMU lanes check them, they are not timings). `go test -bench Binop32` times each kernel against the scalar loop; the
NumPy rows of `bench/perf` are deferred (see `docs/perf-exempt.md`).

### Pairwise `Maximum`, `Minimum` (float64)

| function | computes | NumPy |
|---|---|---|
| `Maximum(dst, a, b)` | `dst[i] = max(a[i], b[i])` (the Go builtin) | `np.maximum` |
| `Minimum(dst, a, b)` | `dst[i] = min(a[i], b[i])` (the Go builtin) | `np.minimum` |

The "K1 remainder" of go-ndarray/ndarray#98 (and #118), which ran them as scalar
loops. The contract is the language's rule, the one `runtime/minmax.go` spells out,
the same on every kernel, bit for bit (and, where no kernel runs, the builtin loop itself):

- **NaN**: a NaN in either operand gives that NaN unchanged (sign, payload, quiet bit:
  a signalling NaN stays signalling); two NaNs give `b[i]`. `max(NaN, +Inf)` is NaN.
- **Zeros**: `max(-0, +0)` and `max(+0, -0)` are `+0` (the bitwise AND of the two
  zeros), `min` of them is `-0` (the OR), whatever the operand order. (NumPy returns
  `a` when `a >= b`, so for a `(-0, +0)` pair it returns the first operand; this
  does not.)
- Otherwise the larger (smaller) operand.

One documented difference from the compiled scalar loop: the Go compiler's own `max`
may quiet a signalling NaN or pick the other operand of two NaNs where the target's
instruction does (`FMAX` on arm64; on amd64 the compiler lowers `max` to
`-min(-x, -y)` with `MINSD`, `MINSD` and `POR`, `cmd/compile/internal/ssa/_gen/AMD64.rules`
lines 196 to 199), so the *payload* of a NaN result can differ from the builtin's on
those machines (`TestPairwiseBuiltin` counts them, per 65536 random pairs, with one
NaN operand / two: arm64 `Maximum` 432 / 131, `Minimum` 424 / 131; amd64 `Maximum`
471 / 99, `Minimum` 502 / 92, the native amd64 CI job). The number results, the zeros and the fact of a NaN are identical. Same
shape as `Add`: the first `len(a)` elements, a panic if `b` or `dst` is shorter, `dst`
may be `a` or `b` (exact overlap only), nothing read or written past a slice. No
float32 variant (the float32 siblings of `Add`, `Mul` and `Sqrt` are `Add32`, `Mul32`, `Sqrt32`).

`MAXPD`/`MINPD`, `FMAX`, `vfmax` and the others cannot give the rule directly
(`MAXPD` returns the second operand for a NaN or two zeros, `FMAX` picks its own NaN,
`vfmax` returns the number), so each kernel is a compare-and-select or an
`FMAX` plus a fix-up, generated by go-asmgen (`maxmin_<arch>_gen.go`), doing the whole
blocks of eight elements with the Go code finishing the last seven:

| target | how |
|---|---|
| amd64 AVX2 | `VCMPPD` (a<b, unordered b, a==b), `VBLENDVPD` twice, `VANDPD` / `VORPD` for the zeros |
| amd64 without AVX2+FMA | the same in SSE2 (`CMPPD`, `ANDPD` / `ANDNPD` / `ORPD`) |
| arm64 NEON | `FMAX` / `FMIN` (right for numbers and zeros), `FCMEQ` of each operand with itself and two `BSL` put the NaN back |
| ppc64le VSX | `xvcmpgtdp`, `xvcmpeqdp`, `xxsel`, `xxland` / `xxlor` |
| s390x vector facility | `VFCHDB`, `VFCEDB`, `VSEL`, `VN` / `VO` (z13, no `VFMAX`) |
| loong64 LASX | `XVFCMP.CLT/CEQ/CUN.D`, `XVBITSEL.V`, `XVAND.V` / `XVOR.V` |
| riscv64 RVV | `vmflt`, `vmfne`, `vmfeq`, `vmor.mm`, `vmerge`, `vand` / `vor` |
| fallback (no kernel) | builtin `max` / `min` (the compiler's own lowering) |

Manuals: the Intel SDM pages for `CMPPD`, `BLENDVPD`, `MAXPD` (felixcloutier.com
mirror) and the RISC-V V 1.0 specification (`v-spec.adoc`) were opened. The Arm ARM
(JavaScript page), the Power ISA, the z/Architecture Principles of Operation (over
the fetch limit) and the LoongArch manual (581 KB, the compare section not reached)
were **not**: those four rest on execution evidence, the edge tables below, run
natively on Apple silicon (arm64) and under QEMU (ppc64le power8 and power9, s390x
`max` and `z13`, loong64 la464, riscv64 at VLEN 128, 256 and 512), as for
`RoundEven`. The loong64 and ppc64le compare instructions have no Go mnemonic and are
`WORD`s with their mnemonic in a comment.

Tests: every pair of an edge table (±0 both orders, ±Inf, quiet and signalling NaNs of
both signs with payloads, subnormals, equal neighbours) at every position of every
length 0 to 33 and four alignments, random bit patterns with planted ties, zeros and
NaNs over lengths 0 to 257, `dst` aliasing `a`, `b` or both, panics, guard pages, a
CPU-gate-off rerun (SSE2 on amd64, the portable loop elsewhere), an oracle that is
the language rule written independently of the kernels' reference and checked
against the builtin, and `FuzzPairwise` with a committed corpus.

One Zen 3 core (AMD EPYC 7773X, GCC Compile Farm cfarm420, `taskset -c 9`,
`GOMAXPROCS=1`, 1-minute load 2.3 to 2.6, 7 interleaved rounds, medians), the AVX2
kernel against the compiled scalar `max` / `min` loop, ns per call:

| op | n = 1e3 kernel | loop | | n = 1e5 kernel | loop | |
|---|---:|---:|---:|---:|---:|---:|
| `Maximum` | 195.6 | 976.5 | 5.0× | 34 142 | 100 820 | 3.0× |
| `Minimum` | 176.6 | 694.6 | 3.9× | 33 203 | 67 510 | 2.0× |

Where no kernel runs (an architecture without one, loong64 without LASX, riscv64
without V, ppc64le before POWER8) `Maximum` and `Minimum` are the builtin loop itself,
`dst[i] = max(a[i], b[i])`, the compiler's own lowering: exactly what go-ndarray ran, so
nothing there is slower or different than before (its NaN payload is the target's; on
riscv64 the builtin returns the canonical NaN, seen under QEMU). The
last seven elements of a kernel call use a rule loop (the builtin for two numbers, the
NaN rule when the result is a NaN) so that one call follows one rule; the tests hold

### `Exp`, `Log` (float64) and `Float32Exp`, `Float32Log`

| function | computes | parity with NumPy |
|---|---|---|
| `Exp(dst, src)` / `Log(dst, src)` | `exp` / `log` of every `src[i]`, float64, 0.511 / 0.519 ULP (Arm optimized-routines, MIT) | **tolerance** (ULP-bounded, not NumPy's bits) |

| `XpbyNoFMA(x, beta, y)` | `y[i] = x[i] + beta*y[i]` (`x + beta*y`) |
| `Axpby3NoFMA(dst, alpha, a, beta, b, gamma, c)` | `dst[i] = alpha*a[i] + beta*b[i] + gamma*c[i]`, left to right |
| `AxpyRowsNoFMA(a, x, ldx, y)` | `y[j] = (((y[j] + a[0]*x[j]) + a[1]*x[ldx+j]) + …)`, unfused, rows in increasing order: the bits of `len(a)` `AxpyNoFMA` calls with `y` loaded and stored once — one row of an exact matrix product (2.1× the `AxpyNoFMA` loop at 100×100, M4 Max) |
| `AxpyDiffNoFMA(dst, a, f, b, c)` | `dst[i] = a[i] + f*(b[i] - c[i])` — the differential-evolution mutation (rand/1, best/1; `dst = a = c = b` gives `b += f*(x - b)` of rand-to-best/1) |
| `Polyval(dst, x, c)` | `dst[i] = polyval(x[i], c)`, `numpy.polynomial.polynomial.polyval(x, c, tensor=False)`: `c0 = c[-1] + x*0; c0 = c[-i] + c0*x` |
| `Chebval(dst, x, c)` | `dst[i] = chebval(x[i], c)`, `numpy.polynomial.chebyshev.chebval(x, c, tensor=False)`: Clenshaw, `x2 = 2*x`, `c0 = c[-i] - c1; c1 = tmp + c1*x2`, then `c0 + c1*x` |

`Axpy`, `Xpby` and `Axpby3` are **fused**: one rounding per element, which is the
more accurate result and what BLAS does, but not what NumPy does. NumPy never
fuses: `y + alpha*x` is two ufunc calls, a multiply that rounds into a temporary
and an add that rounds again, and `a + F*(b - c)` is three. A solver validated by
exact equality against SciPy (differential evolution, basin hopping) has to take
that path, so these kernels round **every product and every sum on its own, in the
order NumPy evaluates the temporaries**, and are bit-identical to the NumPy
expression on every architecture (the payload of a NaN that an operation itself
creates, `Inf - Inf` or `0*Inf`, aside; a NaN that is the only NaN operand keeps
its sign and payload, as in NumPy).

amd64 (AVX2, same gate as the other kernels) uses `VMULPD`/`VADDPD`/`VSUBPD` and
arm64 `VFMUL`/`VFADD`/`VFSUB` — never a fused instruction; both are ×4 unrolled
with a 1-vector loop and a scalar tail, never read or write past a slice (guard
page tests), and allow `dst` to be the very slice of an input. The portable code
(`ppc64le`, `s390x`, `riscv64`, `loong64`, 32-bit) writes every product through an
explicit `float64(...)` conversion, which the Go specification says prevents the
compiler from fusing `x*y + z`; without it a plain Go loop is *not* NumPy's
arithmetic on those architectures (nor on arm64).

Validated against NumPy 2.5.4 on 13 088 committed fixture cases (the inputs are
regenerated from seeds, the fixture holds a SHA-256 prefix of NumPy's result bits
per case): the four kernels × ten input families (uniform, wide exponent,
cancellation in `b - c`, rounding ties, ±0, `-0` only, `+Inf`, one NaN, ±Inf / NaN of
both signs / ±0) × every length 0..300 and the block boundaries, plus 1e3 / 4097 /
100 001 — 0 mismatches on arm64 and on amd64, from the same fixture. A planted
**fused** variant (`math.FMA`) differs from the fixture in 1 400 to 1 800 cases per
operation, and planted **reordered** variants (`a + (F*b - F*c)`, right-to-left
sums) in 700 to 2 800, so the fixture can tell them apart. Regenerate with
`NOFMA_REGEN=1 go test -run RegenerateNoFMA .` (needs `uv`, or `NUMPY_PYTHON`).
`FuzzNoFMAKernels` checks the SIMD kernels against the portable loops.

### Reproducing `np.sum`: `SumPairwise` (float64)

| function | computes |
|---|---|
| `SumPairwise(a)` | `Σ a[i]`, **bit-identical to `np.sum(a)`** for a contiguous 1-D float64 array; `+0` for an empty slice |

`Sum` adds in the lane order of the SIMD kernels, which is fast but is not
NumPy's order, so its last bits differ from `np.sum`. When a result must be
reproducible against NumPy (a stopping test comparing `np.std` of a population
with a tolerance, a regression against a NumPy oracle), use `SumPairwise`. It is
NumPy's pairwise summation, transcribed from `DOUBLE_pairwise_sum`
(`numpy/_core/src/umath/loops_utils.h.src`, v2.5.3): fewer than 8 elements are added
left to right from `-0`; up to `PW_BLOCKSIZE` = 128 elements are summed with
eight independent accumulators, folded as
`((r0+r1)+(r2+r3)) + ((r4+r5)+(r6+r7))`, then the non-multiple-of-8 rest is
added one by one; a longer block is split at `n/2` rounded down to a multiple of
8 and the two halves are added. `np.add.reduce` then adds the result to its
initial `+0`, so a slice holding only `-0` sums to `+0`, as in NumPy.

It is **bit-identical on every architecture**: the order is fixed in the code,
not by the width of a vector register, and no step is a fused multiply-add.
**The 8..128-element blocks run in SIMD** on amd64 (AVX2: the eight accumulators
`r[0..7]` are two 4-lane YMM registers, `VADDPD` per step, the fold
`((r0+r1)+(r2+r3)) + ((r4+r5)+(r6+r7))` by `VHADDPD` + `VEXTRACTF128` + `VADDSD`) and
arm64 (NEON: four 2-lane registers, `VFADD` per step, the fold by `VFADDP`),
and on ppc64le (VSX), loong64 (LASX), riscv64 (RVV, one `vl=8` group) and s390x
(VX), with the same accumulator-per-lane structure:
every lane receives exactly the additions NumPy's scalar code performs on its
`r[j]`, so the bits do not change. The recursion, the `n < 8` start from `-0`,
the `n % 8` tail and the initial `+0` stay as above; the other architectures run
the portable Go block, which is also the reference the tests compare the SIMD
blocks against (`TestSumPairwiseSIMDMatchesReference`, every length 0..700 at
eight start offsets, on raw bit patterns).

Validated against NumPy 2.5.4 on 6 990 committed fixture cases: every length
0..300 for nine value families (uniform, wide exponent, cancellation, ties at
the rounding edge, ±0, `-0` only, `+Inf`, one NaN of either sign, a mix of
±Inf / NaN / ±0), both sides of every block boundary `128·2^j ± 12` up to
`j = 13`, and 1e5 / 1e6 / 2^20 with odd lengths around them — 0 mismatches.
A NaN result is compared bit for bit when exactly one NaN enters the sum; with
several NaNs (or `+Inf` and `-Inf`) which NaN comes out is hardware-dependent
(in NumPy as here), so only "is NaN" is compared. The fixtures are regenerated
with `SUMPW_REGEN=1 go test -run Regenerate .` (needs `uv`); `FuzzSumPairwise`
checks against an independent index-based transcription.

## How the SIMD is built

Every kernel is an FMA-based vectorised reduction: a multi-lane accumulator folded
with a fused multiply-add at the vector stride, then a horizontal reduce and a
scalar tail.

| arch | ISA | FMA op | notes |
|---|---|---|---|
| amd64   | AVX2 + FMA3 | `VFMADD231P{S,D}` | runtime-gated on `cpu.X86.HasAVX2 && HasFMA`; scalar fallback otherwise. `Dot`, `Sum`, `Distance` and the float32 forms run **eight independent vector accumulators** (the FMA/ADD latency of 4 cycles, 2 ports, otherwise caps one chain at a quarter of the issue width); `CDotC` runs eight too. Measured on a Zen 4 core, single-threaded, old/new: `Dot` n=1000 3.2x, n=4096 1.9x, n=1e6 1.6x; `Sum` 4.3x / 5.0x / 2.5x; `Float32Dot` 2.5x / 3.4x / 1.7x; `Float32Sum` 3.5x / 5.1x / 2.6x; n <= 16 is within 0.2-0.5 ns of before. The summation order is therefore unspecified: the contract is the bound `gamma_n * sum\|terms\|`, asserted against a 512-bit `math/big` oracle (`TestReductionsMeetErrorBound`) |
| arm64   | NEON | `VFMLA` | `Dot`, `Sum`, `Distance` and the float32 forms run **eight independent accumulators** (16 float64 or 32 float32 per iteration; a shorter input skips the unrolled loop and its fold); baseline, no gate. Measured on a GitHub `ubuntu-24.04-arm` runner (Neoverse), old/new interleaved in one job, A/A within 1.00-1.04: `Sum` n=1000 3.4x, n=4096 3.5x, n=1e6 1.8x; `Distance` 1.7x / 1.8x / 1.2x; `Float32Sum` 3.1x / 3.3x / 1.7x; `Float32Dot` 1.2x / 1.2x / 1.0x; `Dot` is load-bound and unchanged (0.98-1.07x); n <= 16 is no slower than before |
| riscv64 | RVV | `VFMUL`+`VFREDOSUMVS` | length-agnostic `VSETVLI` stripmining; gated on `cpu.RISCV64.HasV` |
| s390x   | vector facility (**big-endian**) | `VFMADB`, `VFMASB` | all six reductions (float64 and float32 `Dot`, `Sum`, `SumSqDiff`) run **eight independent accumulators**; the float64 kernels are the z13 baseline, the float32 ones need the vector-enhancements facility 1 (z14, gated on `hasVXE`, else the lane-blocked scalar reference) and their `.SB` ops (`VFASB`, `VFSSB`, `VFMASB`) are `WORD`-encoded because the released assembler has none; float64 below 16 elements uses a four-accumulator Go loop (n=8 `Dot` 7.5 to 6.2 ns, n=12 11.8 to 7.4 ns). The `.s` files are committed; regenerate with `go run *_gen.go` (the generators
are build-tagged `//go:build ignore`). All six are validated in CI — amd64/arm64
natively, the other four under QEMU (`tonistiigi/binfmt`) — at **100 % test
coverage**, with differential tests and `FuzzDot`/`FuzzDistance`/`FuzzAxpy`
against the scalar reference on every architecture. The elementwise kernels are
also checked bit for bit against `math.FMA` for every length 0..257 at four
element offsets, and run on slices placed right against `PROT_NONE` guard pages
so that a vector load past either end would fault.

## Floating-point determinism

A SIMD reduction does not add its terms left-to-right: it keeps several
independent accumulator lanes (for instruction-level parallelism) and folds them
at the end, so its rounding differs from a naïve scalar loop. For dot / distance
/ cosine, bit-exactness against a naïve loop is neither meaningful nor required —
correctness to a few ULP is.

So the reference the tests and fuzzers check against (`dotLanes`, `sumSqDiffLanes`,
…) reduces in the **same lane-blocked order** the kernels use, and each kernel is
required to match it to a tight, documented relative tolerance (`1e-12` for
float64, `1e-5` for float32) on **every** architecture. The differential tests
and fuzzers enforce this, making the results deterministic and consistent across
arches.

  the sequential loop's (and `numpy.max`/`numpy.min`'s): NaN if any element is
  NaN, `-0` below `+0`, a panic on an empty slice. Tests: NaN and zeros at every
  position of every length up to 100 (every lane and tail slot), `PROT_NONE`
  fences on amd64 and arm64, a CPU-gate-off rerun on the four QEMU targets, and
  `FuzzExtrema32` (nightly in `fuzz.yml`, seed corpus in CI).
- The s390x CI lane runs QEMU's `max` CPU model (the float32 kernels need z14).

## Changes in v0.12.0

- `Polyval(dst, x, c)` and `Chebval(dst, x, c)`: Horner and Clenshaw evaluation
  of one series at many points, in the order of `numpy.polynomial` 2.5.4
  (`polynomial/polynomial.py` `polyval`, `polynomial/chebyshev.py` `chebval`),
  unfused, bit-identical to NumPy's result (fixtures built in a linux/amd64
  container). AVX2, SSE2 (no AVX2+FMA) and NEON kernels; ppc64le, s390x, riscv64,
  loong64 and the 32-bit targets run the portable loop (#30).

## Changes in v0.10.0

- `Max`, `Min`, `Float32Max`, `Float32Min` order `-0 < +0` like NumPy and Go's
  `max`/`min` (#32).
- amd64 CPUs without AVX2+FMA run SSE2 kernels for `Add`, `Sub`, `Mul`, `Div`,
  `Sqrt`, `ClampScalar` (#31).
- ppc64le, loong64, riscv64 and s390x run the `SumPairwise` block and the
  float64 `Add`, `Sub`, `Mul`, `Div`, `Sqrt` kernels (#30; `Max`/`Min` kernels on
  those architectures remain open).
